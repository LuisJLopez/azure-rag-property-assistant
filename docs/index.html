Property Knowledge Assistant

A RAG prototype that answers questions about UK property documents — with citations — built on Azure AI Search and Microsoft Foundry.

Built to learn Blob Storage, indexing, chunking, embeddings, hybrid retrieval and grounded generation. Not a production system, not financial advice.

The pipeline

Documents go in one end; cited answers come out the other. Every node below is a real resource that was created and tested on the day.

  1. Source

    Public UK property PDFs

    Four public guides from gov.uk and parliament.uk: How to Buy a Home, How to Lease, the draft Commonhold & Leasehold Reform Bill guide, and a Commons Library briefing on leasehold reform.

  2. Storage

    Azure Blob Storage

    stpropertykb001 / container property-docs. Holds the originals, unmodified. The indexer is the only thing that reads them.

  3. Extract · chunk · embed

    Azure AI Search indexer + skillset

    SplitSkill cuts each PDF into ~2000-character chunks with 500 characters of overlap, then AzureOpenAIEmbeddingSkill calls text-embedding-3-small once per chunk to produce a 1536-dim vector.

  4. Index

    Search index property-kb

    391 rows — one per chunk — each holding the text, its vector and source metadata. Hybrid keyword + vector search with the semantic ranker enabled.

  5. Knowledge

    Foundry IQ knowledge base property-kb-knowledge

    Wraps the index so an agent can query it. Output mode set to extractive, so the agent receives raw retrieved passages and their source references, not a pre-summarised answer.

  6. Agent

    Foundry agent property-agent

    Runs on gpt-5-mini. Instructed to always search the knowledge base first, answer only from what comes back, and say so when nothing relevant is found.

  7. Output

    Grounded answer with citations

    Every claim carries an inline reference that resolves to a specific chunk in the index — a pointer to the evidence, not "trust me".

What it does

  1. Uploads 4 public UK property PDFs to Blob Storage via a small uv-managed Python script, authenticated with az login rather than stored keys.
  2. Azure AI Search chunks each PDF and generates one embedding per chunk through the integrated vectorization skillset.
  3. Chunks, vectors and source metadata land in a hybrid search index — 391 chunks in total.
  4. A Foundry agent queries the index at chat time and answers only from retrieved chunks, with inline citations back to the source document.
  5. A needle-in-a-haystack test: added a one-line document — "Luis's favourite house colour is red" — re-indexed, and the agent retrieved and cited that exact fact instead of guessing from general knowledge.

The bug story

The most useful part of the day. The wizard-built indexer failed every single run at the embedding step — and every obvious explanation turned out to be wrong.

  1. Symptom

    Every indexer run died at AzureOpenAIEmbeddingSkill with DeploymentNotFound — seven failed runs between 12:07 and 14:23, each lasting 1 to 11 seconds. The blob read succeeded every time; only the embedding call failed.

  2. Ruled out, one by one

    • Managed-identity RBAC propagation. Granted Cognitive Services OpenAI User to the Search service's identity and waited 45+ minutes. Still failing.
    • Authentication method. Switched the skill to an API key. The error changed to 401 once (a key for the wrong resource had been pasted), then back to DeploymentNotFound.
    • The deployment itself. Direct REST calls to the same endpoint with the same key returned 200 and a real vector — every time.
    • Deployment SKU. GlobalStandard is the only SKU offered for this model in any region, so it couldn't be the variable.

  3. Root cause

    The embedding model lived on a Microsoft Foundry resource of kind AIServices — the newer, unified multi-service type. Azure AI Search's embedding skill didn't reliably call it. A dedicated resource of kind OpenAI explicitly lists Microsoft.Search as a trusted service; the AIServices one didn't behave the same way.

  4. Fix

    Created property-kb-openai (kind OpenAI, in uksouth — the same region as the Search service), deployed text-embedding-3-small there, and repointed the skillset. Next run: 4 of 4 documents, 0 errors, 3 minutes.

  5. Lesson

    "Works when I call it directly" is not the same as "works when another Azure service calls it." Read the indexer's execution history, not the chat output.

Three things learned

Agentic retrieval is a decision, not a default

With generic instructions, the agent answered a vague question from the model alone and never called the knowledge base — visible only in the Traces tab, not in the chat output. Rewriting the instructions ("always search first; answer only from retrieved documents; say when nothing is found") fixed it.

Resource kind matters

AIServices and OpenAI resources look identical from the REST API. The difference between them was the entire bug — and it only showed up when a different Azure service made the call.

A known gap, left honest

Asked about Japanese mortgage rates (not in the corpus), the agent correctly refused to invent a number — but said "no live web lookup available" instead of the spec's "not found in the supplied sources." Documented as a limitation, not hidden.
